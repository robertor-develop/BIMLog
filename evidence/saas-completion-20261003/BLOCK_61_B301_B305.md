# Block 61 — B301-B305 — payment-confirmation integrity

## Product decision record

- **Problem:** A signed Stripe checkout-completion event could reach activation without independently proving that the canonical subscription checkout was complete and paid or matching its provider customer, currency and amount to the exact BIMLog order.
- **Decision:** Require exact completed-and-paid subscription facts before receipt persistence, repeat the customer/session/subscription/currency/amount/order checks inside the activation transaction, classify rejections without storing secrets, and describe the browser return as verification pending.
- **Customer effect:** A Stripe redirect never claims paid access. Activation requires the exact signed webhook, company, session, customer, subscription, currency, amount and metadata lineage.
- **Security:** Credentials, signatures and provider payment payloads stay server-side.
- **Operations:** This is the first five-build block after the accepted Block 60 publication. Push is due at B305; publication and full authenticated Chrome smoke are due after B306-B310.
- **Rollback:** Revert B301-B305. This block adds no schema migration, provider configuration or customer write outside the existing guarded transaction.

## Builds

- **B301:** Validate a Stripe checkout completion as subscription-mode, complete, paid and carrying canonical subscription, currency and amount facts.
- **B302:** Revalidate exact provider customer, session, subscription, currency, amount and order metadata inside the activation transaction.
- **B303:** Persist precise, secret-safe rejection categories for unsupported state, amount mismatch and lineage failure.
- **B304:** Present Stripe return as verification pending until the signed canonical confirmation activates access.
- **B305:** Bind focused regression coverage and the five-build push boundary into the release gate and Living Brief.
