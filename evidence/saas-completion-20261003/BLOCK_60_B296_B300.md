# Block 60 — prepared-offer checkout continuity

## Product decision record

- **Problem:** after subscription preparation, the workspace exposed only a status. A different plan or billing cycle could still appear selectable even though the server would reject it, and a retry with a new request key could ask Stripe to create another customer.
- **Decision:** project the canonical prepared offer to the authenticated company workspace, validate it strictly, lock the selectors to that offer, require an exact offer match before checkout, and use one company-stable Stripe customer idempotency key.
- **Alternatives considered:** relying only on the server checkout rejection leaves a misleading conversion path; automatically redirecting into Stripe removes the user’s explicit checkout action.
- **Tradeoff:** changing an already prepared offer still requires an explicit governed subscription-change workflow. The page now states this truth instead of implying an unsupported edit.
- **Security and privacy:** the browser receives only subscription identity, plan, billing cycle and seat count. Provider customer references, credentials and payment data remain server-side.
- **Operations:** B296-B300 reach the ten-build publication boundary with B291-B295. Full exact-head gate, one push, exact-source publication and authenticated Chrome smoke are required.
- **Rollback:** revert B296-B300 together; no schema migration or irreversible provider mutation was introduced.

## Builds

- **B296:** project the canonical prepared subscription offer into the company workspace.
- **B297:** fail checkout eligibility closed when the selected offer differs from canonical authority.
- **B298:** align and lock the bilingual billing UI to the prepared offer and show its seats.
- **B299:** make provider-customer retry identity company-stable and return an exact setup receipt.
- **B300:** bind focused acceptance, evidence and the ten-build release boundary.
