# Build 03 — role and authority trace

This is a source-level trace, not a signed-in test of six people. The only authenticated browser account in this block was Roberto Rodriguez / RRY Asociados.

| Required role | Existing enforcement | Gap for acceptance |
| --- | --- | --- |
| PMO/template author | `routes/delivery-workflow-templates.ts` and `routes/workflow-governance-policies.ts` derive company scope from the authenticated user; write requires Super Administrator or an active `company_master_catalog_administrators` grant. Both scope records by company. | Confirm the PMO author's actual company grant and create/save/reopen in a controlled QA company. No grant is inferred from a visible page. |
| Reviewer/approver | Governance policy approval requires a different creator/latest editor and an effective company Finance `cost_approver` grant. Delivery Workflow economic-allocation approval also requires a separate Finance checker; a workflow without economic allocation does not use that economic checker path. | Exercise independent checker denial/approval in real accounts and decide/implement the required non-economic workflow review boundary, if policy requires independent review of every template. No self-approval claim is made. |
| Publisher | Both version APIs require PMO write authority, an approved current revision and fingerprint recheck; events and supersession are stored. | Test published-option visibility under a different company member, retirement, stale revision and a second version in live QA. A policy matrix entry does not itself authorize publication. |
| Project Intake user | `delivery-workflow-selection.ts` permits company versions only when published, otherwise uses built-in defaults when company policy allows; multiple matching company versions force explicit selection. Intake binds per-Contract-Item choices. | Prove the exact published Shop/Sleeve options on a new job and ensure a company policy cannot be bypassed by default or stale version. |
| Project Manager | `delivery-workflow-runtime.ts` uses active project membership and explicitly assigned execute/review/approve rows; `job-operations.ts` exposes assignment and step endpoints. | Verify manager authority/assignment, phase gates, audit and reassign behavior with a separate real user. Do not equate the Governance page's free-form role codes with runtime grants. |
| Executor | Runtime `requireRole` checks exact assigned user for an action; legacy Operations time recording prevents ordinary members from recording for another user. | Verify execute and own-time paths as the executor, including save/reload and denial on another user's task. |
| QC reviewer | Runtime checks assigned `review` role and phase QC gates. The separate newer EDT authorization profiles also define QC permissions, but guarded EDT mutation routes remain closed. | Verify QC review, rejection/reopen and independence with the actual QA role; do not count static permission profiles as live authority. |

Source evidence: `artifacts/api-server/src/lib/delivery-workflow-runtime.ts`, `artifacts/api-server/src/lib/edt-engine-authorization.ts`, `artifacts/api-server/src/lib/job-operations-service.ts`, the two company version routes, and `artifacts/bimlog/src/pages/CompanyWorkflowGovernance.tsx`. The Governance UI explicitly states that its configured approval thresholds, change rules and company-role rows are policy intent, not yet execution permissions. This is a confirmed feature gap, not a role-setup problem.
